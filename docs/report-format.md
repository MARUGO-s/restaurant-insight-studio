# 総合分析レポート

## 表示

レポート閲覧時は分析フォームを閉じ、本文の幅を制限した1列レイアウトにする。目次から各章へ移動でき、詳細本文は最初から表示する。比較表はPCではセルを折り返し、スマートフォンでは列名付きの縦表示にする。本文内URLはドメイン名、出典一覧はドメインとパスで表示し、リンク先・ツールチップには完全なURLを保持する。

旧レポートの【見出し】・Markdown見出しと本文を保持して表示する。番号付き施策は「実施内容／根拠・理由／手間・確認先」の表へ変換する。根拠・理由や確認先が複数記載されていても省かない。

## 保存形式

既存の restaurant_insight_reports.report（text）にJSONを保存する。旧形式の文章も互換表示する。JSONの要点は overallAssessment / keyMessage / keyFindings / strengths / actionPlan / limitations、本文は detailSections の配列。

各詳細章は title / body と、任意の columns / rows / sources を持つ。列数と各行のセル数が一致しない最終出力や、途中で切れたJSONは完成レポートとして保存しない。detailedReport は旧形式の詳細本文との互換性を持ち、新形式では導入文として表示する。

## 調査と内容

調査前の「特に調べてほしいこと」は任意入力（2,000文字以内）。空欄・空白のみの場合は従来の調査プロンプトをそのまま使用する。入力がある場合は市場・媒体・Xの各担当、反証・統合へ同じ重点事項を渡し、通常の総合分析に加えて重点事項への回答を記載する。希望に合わせて事実を補うことはしない。

正規化済みの `researchFocus` を `restaurant_insight_runs.input` と保存レポートJSONに保持する。保存時はAI出力ではなく受付時の値を使う。再試行・画面の再読み込み・レポートへの質問でも引き継ぎ、画面には「この調査で指定した重点事項」を表示する。過去レポートの条件を再利用する際も復元する。指定を消すと通常の分析に戻る。旧レポートは重点事項なしとして扱う。

市場・競合、グルメ媒体、X・SNSの3担当が調査し、OpenAIが反証と統合を行う。媒体ごとの取得範囲、商品・条件比較、PR・写真・予約案内、口コミの母数と反例、系列比較、実行手順、30日間の測定計画を含む。公開情報から分からない売上・原価・予約・業者資料の値は補わない。

市場はOpenAI、グルメ媒体はGoogle Gemini、XはxAI Grokが担当し、分析開始前に3社すべてのキー設定を確認する。Geminiが失敗してもOpenAIで代替せず、未完了の専門調査をジョブに保存して再試行する。必須の4調査（市場・媒体・最近のX・過去のX）が所定の提供元ですべて完了した場合だけ統合する。過去レポートの partial / error は未完了として表示し、以前に保存したOpenAI代替レポートは実際の担当名を保持する。検索が成功したうえで対象投稿が見つからない場合は、検索範囲と0件という結果を記録する。API失敗を投稿0件と扱わない。

工程・応答本文は専用ジョブテーブルに都度保存する。市場・グルメ媒体・各X工程は1回最大300秒、最大3回（初回+再試行2回）。2工程合わせて最大30分のAPI処理枠を確保し、全体の待機枠は45分。統合は独立した工程で最大300秒・2回。各工程の応答待ちをSupabaseの400秒以内に収め、1分ごとのCronで実行枠が失効したジョブも回収する。ブラウザーを閉じても継続し、失敗後の手動再開では完了済みの調査を実行し直さない。

## 永続ジョブの検証

`supabase/tests/transport_test.ts` はSSEの分割境界・CRLF・途中切断・完了後の開いた接続、事前料金記録、認証なしの実行拒否を検証する。`supabase/tests/restaurant_insight_durable_jobs.sql` はトランザクションをロールバックし、二重claim・古いlease・途中結果保持・失敗工程だけの再開・統合の原子的保存を検証する。有料APIはこの2つのテストでは呼ばない。

X APIの公式推奨待機時間は900秒以上だが、Supabaseの単一workerは400秒が上限のため、1リクエストを900秒待つ設定は採用しない。検索範囲を分けた300秒の工程、ストリーミング保存、永続キューの再試行を組み合わせる。
参照: https://docs.x.ai/developers/model-capabilities/text/best-practices
参照: https://supabase.com/docs/guides/functions/limits

## Geminiの接続と利用枠診断

「API料金」に「Gemini接続確認」を設け、調査と同じサーバー側APIキー・モデルへ短いGoogle Search有効リクエストを送る。診断はログインユーザーのみ、1ユーザー1分1回に制限し、API利用量は `provider_diagnostic` として通常の料金明細に記録する。接続成功は店舗調査全体の完了とは区別する。キーの値はブラウザーへ返さず、照合用に末尾だけを表示する。

APIエラーではHTTP状態・quotaMetric・quotaId・quotaValue（数値0を含む）・対象モデル・地域・プロジェクト番号・指定待機秒数を許可リストで抽出し、`request_metadata.provider_error` に保存する。料金明細の「提供元が返したエラーの詳細」から確認できる。OpenAIやxAIの利用枠エラーをGeminiの課金不足だと表示しない。前払い残高があっても利用枠エラーの原因はAPI応答と対象プロジェクトの設定を照合して判定する。
