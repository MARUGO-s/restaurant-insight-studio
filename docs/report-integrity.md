# 調査内容の審査と表示の分離

## 状態と対象

保存済みレポートを点検して決めた改善仕様。実装・下記の統合回帰検証・独立レビューを完了。2026-11-01に公開承認を受け、Pagesと両Edge Functionへ反映・配布コード照合済み。公開証跡は[公開記録](release-2026-11-01.md)を参照。保存済みレポートの一括書換え、有料の再分析、DB migrationは実施しない。

対象は特定店舗ではなく、すべての新規レポートに適用する仕組み。個店名、価格、私有レポート本文、認証情報はテストfixtureに持ち込まず、同型の合成例で再現する。

## 原調査と採否

専門AIのAPI応答完了は、本文の全主張を検証できた意味ではない。専門調査本文は消さず、未検証の主張を含む原記録と明示する。

統合時に重要な主張について採用・条件付き採用・未確認・不採用、理由、出典を構造化して記録する。主張は対応する担当AIの原文へ結び付ける。URLが観測資料に含まれることや、引用が原調査に存在することは、原資料との意味一致・店舗実態・因果効果の証明ではない。

口コミの具体的な体験は実読範囲・日付・個別根拠を求め、取得できなければ未確認とする。離脱率、売上、人気、需要を公開条件だけから断定しない。新しい有料検証工程は追加せず、既存の統合呼出しの出力と検査を強化する。

## 訂正した商品と原記録

原商品台帳はサーバー側で全件保持する。一方、読者が使う商品表は各商品IDに対する審査結果から作る。確認・訂正・未確認・不採用を区別し、訂正理由を表示する。商品を黙って消したり、統合本文で訂正した媒体名を原台帳のコピーで上書きしたりしない。

商品審査は全IDに一意対応させ、未知ID、欠落、重複、未知出典を拒否する。未確認・不採用の元情報は確定商品と混ぜず参照記録として扱う。原文と照合後の記録を別に表示する。

## 店舗課題・調査課題・店舗への確認

課題と施策のscopeを `store`（店舗改善）、`research`（調査側の追加確認）、`verification`（店舗への確認事項）に分ける。課題と施策の分類を整合させ、最優先の店舗施策はstoreだけから選ぶ。入力URLの取り違え、取得不能、古い調査との差は、そのまま店舗の掲載不備や経営課題にはしない。

分類のない旧レポートは保存当時の表示を保持する。未知の分類を店舗改善へ自動昇格させない。

## 指標・確認手順・施策選択

指標は分子・分母の対象を揃える。条件欄の確認率は確認済み条件欄数÷全条件欄数、商品単位の完了率は全必須条件確認済みの商品数÷対象商品数と区別する。異なる単位を正当に扱う客単価・転換率等まで一律拒否しない。本文と実行計画で同じ指標の意味を変えない。

予約成立前の画面だけで完了画面・通知メールを確認したことにしない。完了後の確認は既存通知、管理画面、店舗が承認したテスト等を明記し、無断の予約確定や通知送信を提案手順へ紛れ込ませない。

施策は実施条件、手間、リスク、他案との比較、見送り理由を示す。既存の任意入力「特に調べてほしいこと」に店舗の制約や目標がある場合は使い、情報がない場合は推測しない。専用の店舗事情入力欄や非公開経営データ連携は今回追加しない。

## 互換性と費用保護

新規生成はサーバーが新契約を要求する。AIがバージョンを省略しただけで旧検査へ抜けられないようにする。既に完成した旧形式の統合応答は、所有者・実行・ジョブ・料金との既存照合を維持し、追加の有料生成なしで従来の検査を通して復旧できることを別途検証する。

保存済み本文・認証・入力値・送信先・予約データ・料金単価は変更しない。新検査が不合格の完成応答は保持し、確認待ちにする。自動再生成で品質を修復したふりをしない。
